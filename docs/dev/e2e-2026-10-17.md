# End-to-end check on CPU, airgap egress check — 2026-10-17

First run of the whole chain with a real LLM: Streamlit test UI → OpenAI-compatible LLM (a local OpenAI-compatible
test server on the CPU) → MCP tools → PostgreSQL sample release. Everything below was measured on the development
host; nothing was tuned for the questions.

> **Note (2026-10-17, later the same day).** By user decision no LLM runtime is bundled any more: the chat LLM is
> one external OpenAI-compatible endpoint (by default the user's Mistral endpoint, `OPENAI_BASE_URL`), and the local
> test server used here was removed from the stack. The measurements below stay as recorded; the reproduce commands
> at the end are the current ones (the egress check now chats with a deterministic stub, `scripts/openai_stub.py`). Raw reports: `data/reports/e2e/run{1-baseline,2-asof-fix}.json` and `data/reports/egress/…/summary.json`
(build-side data, gitignored).

## Bugs found and fixed

1. **The model invents `as_of`.** Every call carried the model's training-time "today" (2024-04-05, 2024-04-27,
   2025-04-05). The sample stores only the current texts, so every text lookup at that date was empty and every
   answer said that nothing was found. The sidebar documents « as_of (vide = date du serveur) » but the bridge let
   the model's value through. Fix (`ui/lgx_ui/tools_bridge.py` `apply_overrides`, `SidebarOverrides.model_as_of`):
   without a sidebar date the model's `as_of` is dropped and the server date applies; the tool panel shows
   « as_of 2024-04-05 du modèle ignoré (date du serveur) »; a new sidebar checkbox « as_of choisi par le modèle si
   vide » restores the old behaviour. Test: `test_model_as_of_is_dropped_without_a_sidebar_date`.
2. **`resolve_citation` attached other candidates' status warnings to the answer.** For « RGD du 24 juillet 2000
   concernant le travail de candidature » the resolver correctly chose `n3` (confidence 0.93, in force), but the
   envelope also carried `W_REPEALED` of two *other* RGDs of that day (`n1`, `n4`, confidence 0.13), without refs,
   and the model reported the in-force act as repealed. Fix (`lgx_mcp/tools/cite.py`): a resolved reference warns
   only for the chosen act, an ambiguous one for its top three candidates, and every status warning carries the
   candidate's act ELI in `refs`. Contract test: `test_resolved_citation_warns_only_for_the_chosen_act`.
3. **Sidebar values were lost** (seen in the browser, not by AppTest): switching page emptied « Base URL » and
   « Modèle » (streamlit 1.65 drops keyed widget values on a page switch), and in the first browser session after a
   server start the first chat message did the same (its second script run counts as a page switch), which
   disabled the chat (« Aucun LLM configuré »). Fix (`ui/lgx_ui/app_support.py`): every keyed sidebar widget uses
   `persist_state="session"`, takes its default from `st.session_state` (no `value=`) and is re-saved at the start
   of each run. Test: `test_sidebar_widgets_keep_their_values_across_pages`; checked in Chromium on a fresh server.
4. **CPU timeouts.** `compose.dev.yml` now defaults to `LGX_LLM_TIMEOUT_S=600` and `LGX_TURN_BUDGET_S=1200`
   (were 120 s / 600 s); the plan's 120 s assumes the 16–32-core `cpu` profile, not 4 vCPUs.
5. Cosmetic: the Corpus page metric « Vecteurs » showed a truncated « disabled:pr… »; it now says « désactivés »
   (the reason stays in the caption below).

## Observed problems (open)

1. **Latency on 4 vCPUs: 4–9 minutes per answer.** Prompt evaluation runs at ≈ 25 tokens/s and generation at
   ≈ 2.5–4 tokens/s once the context holds 5–7k tokens. The tools + system prompt alone are ≈ 1.7k tokens; the
   compact `structuredContent` of one search with 3 hits is ≈ 8.7k characters (≈ 2.5k tokens) while the server's
   own TextContent for the same result is ≈ 3k characters, and the model spends ≈ 150–200 of its 450–750 answer
   tokens re-typing the disclaimer and attribution that the UI already shows. Options for M2: send the TextContent
   (or a slimmer projection) to a small model, let the UI append disclaimer/attribution, or use a larger hosted model
   (since 2026-10-17 the default is the user's Mistral endpoint).
2. **The model still mentions its invented date** in prose (questions 4 and 5) even though the tool results say
   `as_of = 2026-10-17`. A one-line « date du jour » in the system context would probably fix it; the prompt text
   is Appendix D.6 verbatim, so this is left to the plan owner.
3. **Lexical retrieval misses the obvious article**: « délai de préavis … licenciement » does not return
   art. L. 124-3 (the notice periods) even with `top_k` 10; and the model asked for `top_k` 3. Expected to improve
   with the reranker (M2) and vectors (M3).
4. **Language**: the German question was answered in French, with the German `legal_answer` prompt (which has no
   explicit « antworte auf Deutsch ») and again with the default French prompt, which does say « Réponds dans la
   langue de l'utilisateur » (run 3: same three tool calls, correct verbatim article with ELI, V1–V3 ok, 542 s,
   French). A 4B model does not switch language after French tool output; a larger model or an explicit language
   line is needed for German users.
5. **Small-model reasoning errors**: wrong framing in question 3 (out-of-scope GDPR obligations not flagged),
   an invented « Art. 1 » in question 4, warnings of uncited hits repeated. The verifier (V1–V3) cannot catch
   these; G4-style evaluation with a lawyer is needed before choosing a production model.
6. **Detours**: for « Que dit l'article … » the model calls `resolve_citation` → `get_act` (with the *article*
   ELI) → `get_article` instead of `get_article(citation=…)` directly: two extra LLM rounds (≈ 3 min on CPU).
7. **Citation keys collide across tool calls**: `get_act` and `get_article` both label their source `[C1]`, so the
   Chat page shows two « [C1] » cards and `[Cn]` keys are ambiguous for V2 within one turn.

## Airgap egress check

`scripts/egress_check.sh` (also `make egress-check`) starts db + db-load + mcp + the LLM server + lgx-streamlit as
a separate compose project from `compose.dev.yml` plus a generated override, then runs a scripted browser session.
(Since 2026-10-17 the LLM server of the check is `llm-stub`, the deterministic `scripts/openai_stub.py`; the results
below were measured with the local test server and its real model.)

Method:

- **Network.** Every service is only on `backend`; `edge` and all published ports are removed. `--mode internal`
  (default) keeps `backend` `internal: true`: the containers have no default route (only `172.31.250.0/24`).
  `--mode routed` makes it an ordinary bridge without masquerading, so that a connect to any outside address leaves
  the container and is visible to the counters below.
- **DNS sentinel.** A pinned CoreDNS (`coredns/coredns:1.14.7@sha256:7efd3c63…`, `deploy/images.lock`) on
  `172.31.250.53` is every service's `dns:` server; it logs every query and answers NXDOMAIN, with no upstream.
  Docker's embedded resolver still answers service names (`db`, `mcp`, `llm`) itself, so the sentinel sees only
  external names.
- **Packet counters**, inserted before the first container starts: `DOCKER-USER -i br-lgx-egress ! -o br-lgx-egress
  -j DROP` (anything forwarded out of the bridge) and `INPUT -i br-lgx-egress -m conntrack --ctstate NEW -j DROP`
  (any new connection from a container to the host itself).
- **Browser.** `scripts/ui_browser.cjs` (Playwright, headless Chromium) opens the UI at the container's address,
  asks one chat question (« Que dit l'article L. 121-1 du Code du travail ? », real LLM on CPU), runs one Direct
  search (« art. L. 121-1 C. trav. ») and records every request URL of the page, websockets included.
- **Positive controls** afterwards, from inside `lgx-streamlit`: a lookup of `lgx-egress-canary.example` (must reach
  the sentinel log), a TCP connect to `192.0.2.1:443` (TEST-NET-1; counted by DOCKER-USER in routed mode, fails
  with ENETUNREACH in internal mode) and one to the bridge gateway (must be counted by the INPUT rule).
- **Pass** = 0 sentinel queries, 0 packets on both rules and 0 non-local browser requests during startup and the
  session, and every control observed.

Results:

| | `--mode internal` (20261017T023034Z) | `--mode routed` (20261017T024148Z) |
|---|---|---|
| Startup (`up --wait`, db restore included) | 26 s; 0 DNS queries, 0 / 0 packets | 27 s; 0 DNS queries, 0 / 0 packets |
| Session: chat (« Que dit l'article L. 121-1 du Code du travail ? ») + direct search | 628 s (chat 619 s, answered with ELI and 2 sources) | 639 s (chat 630 s, same answer) |
| Sentinel queries during startup + session | **0** | **0** |
| DOCKER-USER / INPUT packets during startup + session | **0 / 0** | **0 / 0** |
| Browser requests (all to `172.31.250.5:8501`) | 157: 1 document, 148 scripts, 2 stylesheets, 3 fonts, 2 fetch, 1 websocket — **0 non-local** | 157, same split — **0 non-local** |
| Control: canary lookup | logged (A + AAAA) | logged (A + AAAA) |
| Control: connect 192.0.2.1:443 | `ENETUNREACH` in the container (no route), DOCKER-USER +0 | timed out, **DOCKER-USER +3** (SYN + retries) |
| Control: connect to the gateway 172.31.250.1:9 | INPUT +3 | INPUT +3 |
| Verdict | **PASS** | **PASS** |

So during startup, one chat answer (real LLM) and one direct search, none of db, db-load, mcp, the LLM server,
lgx-streamlit (nor the page in the browser) tried to resolve an external name or to open a connection to anything
outside the internal network, and the probes demonstrably see such attempts when they happen. Limits: in
`internal` mode a connect to an IP literal fails inside the container without a packet (no route), which is why
the `routed` variant exists; IPv6 is not enabled on the test network; only page requests are recorded in the browser
(Chromium's own background traffic is not the application's and runs on the connected host anyway).

Earlier attempts, for the record: the first run failed to start because the pinned CoreDNS binary carries the
`cap_net_bind_service` file capability and `cap_drop: [ALL]` makes its `exec` fail (fixed with
`cap_add: [NET_BIND_SERVICE]`); the second run showed 0 / 0 / 0 as well but its chat step failed on sidebar bug 3
(empty LLM fields in the first session of a fresh server), which is how that bug was found.
