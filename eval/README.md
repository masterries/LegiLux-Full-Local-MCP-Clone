# Evaluation (PLAN §11)

Gold sets, the harness that scores them and the reports. Every set here is **`draft_unvalidated`**: written or
generated by the developer on the 2026-10-16 **sample** release, lawyer review pending (PLAN §13 M2, ≈ 4 ld).

| Set | File | Items | How it was built | Scored by |
|---|---|---|---|---|
| G0 smoke | `gold/G0/smoke.json` | 20 | merged in M2 from the contract-test set and the Streamlit Eval tab's dev set (union of checks, `lgx_ui.evalg0` format) | `checks` on `structuredContent`; gate 20/20 |
| G1 citation resolution | `gold/G1/citations.json` | 564 (v2) | `gen-g1`: generated from database facts (code articles in 8 styles, 1er / bis / range members, ELIs in 6 forms, dated acts with and without title, Mémorial A, aliases; v2: 432 resolved, 111 ambiguous, 17 not-found, 4 out-of-scope) — rules in `harness/gen_g1.py` | `resolve_citation`: exact accuracy, citation precision, ambiguity P/R, not-found accuracy |
| G2 retrieval v1 | `gold/G2/retrieval.json` | 205 (185 FR, 10 DE, 10 EN) | hand-written questions over the sample's articles (codes, Constitution, NCPC, CNPD law, copyright, press law, AIFM, small acts), 1–3 targets each, frozen by `freeze-g2` (key, act, article, `text_sha256`) | `search_legislation` top 20: Recall@1/5/10/20, MRR@10, nDCG@10, act-level Recall@10 |
| G3 mandatory warnings | `gold/G3/warnings.json` | 199 (v2) | `gen-g3`: the PLAN §8.5 triggers applied to database facts (`lgx.serving_at`, flags, units, data-quality rows) for every act with text, one article each, search hits, repealed / future / stale / clock / out-of-scope cases, and forbidden codes | share of expected (item, code) pairs present (gate 100 %), forbidden codes (0), status statements (≥ 98 %) |

G1 and G3 are regenerated per release (`gen-g1`, `gen-g3`); v2 = the M2 integration release with the PDF codes (v1, 566 /
184 items, is in git history and in Task B's reports). G2 is frozen; `freeze-g2` checks its targets, and items whose
target changed are re-validated by hand (`revalidated` note; M2: G2-181 / G2-182). Fixed subsets for CPU-bound reranked
runs live in `gold/subsets/` (`G2-rerank-40.json`, `G3-rerank-search.json`; not gold sets themselves).

G4 (end-to-end with an LLM) and G5 (fabrication bait) are M4. The M2 baseline (lexical vs lexical + reranker, all
four sets, knob sweep, reranker cost) is `reports/m2-baseline.md`; the decision it supports is
`docs/adr/0001-lexical-ranker.md`.

## Run

```sh
python -m eval.harness run --set G2 --mode lexical                 # in process, dev runtime DB (lgx_ro), reranker off
python -m eval.harness run --set G2 --mode rerank --rerank-k 16 --rerank-body-chars 600   # TEI at :8090 (LGX_RERANK=on)
python -m eval.harness run --set G2 --ranker rank_cd                 # the M1 lexical ordering (needs a search-API-2 DB)
python -m eval.harness run --set G2 --no-expansion --opts '{"header_weight": 0.5}'   # ablations / tuning knobs
python -m eval.harness run --set G1 --url http://127.0.0.1:8000/mcp --token lgx-dev-mcp-token   # a running server
python -m eval.harness compare eval/reports/G2-*.json                # side-by-side Markdown
python -m eval.harness subset --set G2 --size 40                     # fixed stratified subset → gold/subsets/G2-rerank-40.json
python -m eval.harness run --set G2 --mode rerank --subset eval/gold/subsets/G2-rerank-40.json   # ≈ 11 min on 4 vCPU
python -m eval.harness compare --subset eval/gold/subsets/G2-rerank-40.json eval/reports/G2-*.json   # same ids only
python -m eval.harness gen-g1 | gen-g3 | freeze-g2                    # rebuild the generated sets from a database
```

`--dsn` selects the database (default `postgresql://lgx_ro:lgx-ro-dev-only@127.0.0.1:55432/legilux`). Reports go to
`eval/reports/<set>-<mode>-<ranker>…{json,md}` (`--tag` names them). The in-process backend runs the server's own
`run_tool` (validation, envelope, retrieval, warnings) with the clock pinned to noon of T; G3 items may pin their
own clock (`W_CLOCK_SUSPECT`; skipped over `--url`). `lgx eval …` is the same CLI (registered in `lgx_ingest/cli.py`
when the repository's `eval/` package is importable).

Reranked runs cost 10–45 s per search on this host: run them on the fixed subsets and never two at a time (`make eval
EVAL_MODE=rerank …`). Since the M2 integration the dev runtime database `legilux` carries search API 2, so every run
uses the default DSN. Task B measured the « before » numbers on a scratch copy of the pre-PDF sample release with the
new search functions (obsolete now; kept for reproducing those reports):

```sh

docker exec -i lgx-dev-db pg_restore -U postgres -d legilux_eval_m2 --no-owner --no-privileges < data/bundles/data-2026-10-16-sample.dump
docker exec -i lgx-dev-db psql -U postgres -d legilux_eval_m2 -q < db/schema/95_roles.sql
# replace the three search functions by the M2 ones (DROP FUNCTION lgx.search_candidates(...9 args...), then the
# CREATE FUNCTION statements of 40_search.sql for lgx.query_terms and lgx.search_candidates), ANALYZE
python -m eval.harness run --set G2 --dsn postgresql://lgx_ro:lgx-ro-dev-only@127.0.0.1:55432/legilux_eval_m2
```

## Caveats

* Same author for G2, the curated query expansion and the ranker; the expansion list was written before the
  questions from general legal vocabulary, and the knob defaults were checked on both halves of G2 (odd / even
  items) — still, G2 v1 measures « questions a developer asks », not lawyers' questions. Report ablations.
* G2 DE/EN items are sent untranslated (the worst case: the LLM ignored the tool description's « translate into
  French legal terms »).
* The sample is small (10,220 chunks); idf values and latencies at full scale (≈ 400k chunks) differ.
* Items carry `text_sha256` of their target articles: after a data change, items whose texts changed must be
  re-validated (PLAN §11.1 drift rule) — `freeze-g2` reports them by failing or by a changed hash.
